# /test 补单测

## 什么时候用

- 写完函数没写测试，心虚
- /review 指出来"关键分支无覆盖"
- 重构前先补测试当安全网

## 调用方式

```
/test <函数名或文件路径，可指定测试框架：pytest/unittest>
```

## 工作流

1. **先列用例清单**：在写代码前，先列出要覆盖的用例，分三类——正常路径、边界条件（空输入、0、最大值、None）、异常路径（抛错、非法输入）。清单给用户过一眼再动手。非交互环境（无人值守执行、无法等用户过目）时不等确认，默认按清单继续，并在输出开头标注 `[清单未确认-已继续]`。
2. **写测试**：按清单写，用项目已有测试框架（没框架默认 pytest）；每个用例一个函数，命名说清楚测什么，如 `test_batch_settle_缺失level时给默认值`。测试文件放哪：有 `tests/` 目录就放里面，没有就跟被测文件同目录，命名 `test_xxx.py`。
3. **跑一遍**：写完必须真实执行；失败的用例先判断是测试写错还是代码有 bug——是 bug 就报出来，不要为了绿而改测试迁就 bug。
4. **覆盖率说明**：最后说明哪些分支还没覆盖、为什么（比如"网络超时分支需 mock，已略过"），不撒谎说"全覆盖"。

## 输出格式

```markdown
## 用例清单
- 正常：xxx
- 边界：xxx
- 异常：xxx

## 测试代码
（文件路径 + 完整代码）

## 执行结果
（粘贴真实运行输出：x passed, y failed）

## 未覆盖说明
- xxx：原因
```

## 输入输出示例

输入：`/test calc_discount`

输出要点：用例：gold 8 折 / silver 9 折 / normal 原价 / 未知 level 走默认 / total 为 0 / 负数 total；生成 test_orders.py；真实跑 `pytest`；报告 6 passed。

## 反模式（什么时候不要用）

- 代码本身还没跑通过——先让代码 work，再补测试
- 只想要覆盖率数字好看——这个命令按三类用例写，不刷数字
- 测试依赖外部服务（数据库/网络）且没法 mock——先解决可测试性，硬写出来的测试是 flaky 的源头
- 要求"一次写 50 个用例"——分批写，先核心路径
