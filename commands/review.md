# /review 清单式代码评审

## 什么时候用

- 写完一个功能、准备提交前自查
- 评审别人的 PR，想给"能动手改"的意见而不是"感觉不好"
- 接手一段陌生代码，快速找出风险点

## 调用方式

```
/review <文件路径或粘贴代码，可附背景：这是做什么的>
```

## 工作流

1. **先读全**：把涉及的文件读完，理解意图后再下判断；不确定的意图标 `[推测]`，不按推测扣分。
2. **五轴检查**（每个维度只说真问题，不凑数）：
   - 正确性：边界条件、空值、异常路径、并发
   - 安全：注入、敏感信息、权限、资源未释放
   - 可读性：命名、函数长度、注释是否说清"为什么"
   - 性能：明显的数量级问题（N+1、重复计算、大对象拷贝）
   - 测试：关键分支是否有用例覆盖
3. **分级输出**：`[必须改]`（bug 或安全）/ `[建议改]`（可读性、性能）/ `[可忽略]`（个人偏好，最多 2 条）。
4. **每条意见格式**：`文件:行号 — 问题一句话 — 为什么这是问题 — 改法建议（给代码片段，不只说"建议优化"）`。文件:行号用行内代码标记，不要包 markdown 链接。
5. **上限 10 条**：超过 10 条说明代码需要重构而不是评审，直接说"建议先重构再评审"并给出重构方向。

## 输出格式

```markdown
## 评审结论
（一句话：可合并 / 需修改后合并 / 建议重构）

## [必须改]
- `orders.py:8` — 文件打开后未关闭，异常时泄漏句柄 — 用 `with open(...)` 包裹：
  ```python
  with open(path) as f:
      return json.load(f)
  ```

## [建议改]
- ...

## [可忽略]
- ...
```

## 输入输出示例

输入：`/review /tmp/cmdtest/orders.py，这是订单折扣计算模块`

输出要点：[必须改] 文件未关闭（orders.py:8）、`o["level"]` 缺失 key 时崩溃（orders.py:26）；[建议改] 浮点金额未舍入到分、`summarize` 统计与打印混杂；结论：需修改后合并。

## 反模式（什么时候不要用）

- 代码还没写完、自己都知道是草稿——先写完再评，半成品评审浪费双方时间
- 只想听夸奖——这个命令只说真话
- 超过 500 行的大文件一次性评审——先拆小（按模块分次 /review），否则意见会水
- 风格之争（单引号还是双引号）——不在此命令讨论，用 linter 解决
